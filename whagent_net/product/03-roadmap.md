# Roadmap

Part of [`whagent_net/PRODUCT.md`](../PRODUCT.md). Milestone definitions only. Live status is tracked as `Ledger: M<n> → <status>` comments on the product tracking issue (`tools/project-manager/CONVENTIONS.md` § Roadmap ledger); every milestone below is `not started` until a ledger comment says otherwise. Each milestone is designed with `/project-manager:design <tracking-issue> --milestone M<n>`, and its entry here is that design pass's scope contract. `Cn` ids refer to [`02-capability-map.md`](02-capability-map.md); `LBn` ids to the Load-bearing decisions in [`PRODUCT.md`](../PRODUCT.md).

Ordering rationale: M1 lays down every wire shape (LB1–LB7) behind a Claude-Code-only surface so the shapes get exercised by a real consumer before any UI is built on them; M2 puts the standalone UI on those shapes and adds the cold tier, so the transcript record is read from all three tiers before any other domain binds to it; M3 takes the same component into a host domain, which is the first time another domain binds to whagent-net's bus and identity contracts.

### M1 — An operator can run a capped, tool-enabled session as themselves against ASS's MCP server from Claude Code, and read its transcript

Delivers: C1, C2, C3, C4, C5, C6, C7, C8, C9, C11, C12
Must not foreclose: LB1, LB2, LB3, LB4, LB5, LB6, LB7 — M1 establishes all seven. LB1 and LB7 are the two M1 does not consume itself: the transcript record must be published to the bus on commit in its final shape even though nothing reads it yet, so that C14/C17/C19 can bind to it later without a re-publish format.
Deliberately deferred: headless service-account callers (C10 → M2; LB2's `kind human|service` subject shape is fixed in M1 so nothing forecloses it); live event following for programmatic clients (C17 → M2); cold-tier reads and the archiver (C18 → M2; the hot tier is not TTL'd until the archiver exists, so nothing ages out in M1 and "no retention job" is an M1 design constraint); any UI (C13–C16 → M2); whagent-side tool filtering (C22 → Later; `allowed_tools` is a field on the definition per LB5 but is not enforced).
FR budget: 12
Design-time notes (not FRs): Temporal workflow versioning discipline for open long-lived sessions across deploys is an M1 NFR (Q8). `iss` is a real column on both `subject` and `on_behalf_of` (LB2) — no Keycloak-only CHECK, no bare `sub` — so a non-Keycloak issuer in M3 is a row, not a migration. Consumer-side work M1 depends on, owned by `audience_score_system` under C12: mount `libs/go/whagent`'s verifying middleware ahead of `mcpauth` on ASS's MCP server, and have ASS's `CallerResolver` map the verified `(iss, sub)` → `person_id` from day one (keyed on the pair, so the M3 Google issuer is one more row-set, not a re-key); a Keycloak role for the first agent must exist in the realm. Budget honesty: eleven capabilities in twelve FRs is one FR each plus one spare — design must write C1 (gRPC + Claude Code MCP surface) and C6 (turn cap, cost cap, estimation) tightly. If the draft still exceeds budget with every FR tracing, the next cut is already agreed: C9 stays, C8's role check stays, and C5's per-session override moves to M2 (the definition-level model choice stays).

### M2 — An operator can start a session and watch any session — live or long finished, whoever started it — from a standalone web UI

Delivers: C10, C13, C14, C15, C16, C17, C18, C27
Must not foreclose: LB1, LB2, LB3, LB6, LB7 — the UI reads the LB1 record via the LB7 exchange (no private read path), and the cold tier stores that same record, so a finished session's transcript read from S3 is the record the live view showed; "started by" renders from LB2's subject columns without adding a UI-only identity notion; usage shows from LB6's per-turn rows rather than a counter; LB3 because C10 is the first time the persona JWT is minted for a service subject with no human behind it — same claim set; `sub` is the acting service subject when the caller acts for itself (LB2: `on_behalf_of` = `subject`), never a second claim shape for service sessions.
Deliberately deferred: embedding in another domain's UI (C19 → M3); per-turn context view (C24 → Later); cross-session rollups (C25 → Later); parent/child session views (C21 → Later); agent definition authoring in the UI (not a mapped capability — definitions stay config-seeded per LB5 until someone asks). Pre-agreed over-budget cut, taken only if the design draft exceeds budget with every FR tracing correctly, in this order: C17 → M3 first (C14 already gives humans live following, and M3's host UI subscribes to the exchange directly per LB7, so nothing in M3 depends on C17), then C16 → Later. Never widen an FR to keep a capability in.
FR budget: 12
Design-time notes (not FRs): C10 is carried from M1 and is expected to be one FR — a client-credentials caller passes the same C8 role check with `on_behalf_of` = the service subject and `kind = service` — and C15's "who started it" is what makes those sessions visible. C14 and C17 are independent consumers of the same bus (Q7); the UI binds `htmxsse.Hub` to `whagent_net/events` directly, and `api.StreamEvents` fronts the same exchange for clients without RMQ credentials. C18 brings the archiver (batch → gzip → S3 → index row; `manmanv2/log-processor/archiver` is the precedent) and, with it, the first hot-tier retention rule; the read path must resolve a session's transcript across hot and cold tiers without the reader knowing which served it.

### M3 — An ASS Creator / Analyst can run a research agent inside ASS's web UI that acts as them against ASS's MCP tools

Delivers: C19, C20
Must not foreclose: LB1, LB2, LB3, LB7 — the embedded component is a reader of the same record and exchange as the standalone UI, and the on-behalf-of chain is the same LB3 credential ASS already verifies since M1.
Deliberately deferred: parent/child sessions (C21 → Later); whagent-side tool filtering (C22 → Later); mid-flight tool-set changes (C23 → Later); per-turn context debugging (C24 → Later); usage rollups (C25 → Later); Slack front door (C26 → Later).
FR budget: 12
Prerequisites (outside this product, before M3 enters design): an amendment to ASS's brief (`/project-manager:product` on ASS's tracking issue #1562) touching three things together — its LB4, the "never a chat/reasoning surface" clause of its LB5, and its non-goal — narrowing "no hosted agent loop, ever" to "ASS does not host its *own* agent loop — it embeds whagent-net's", since C20 puts the research conversation inside ASS `web`; and ASS `web` taking a RabbitMQ dependency so it can run its own `htmxsse.Hub` on `whagent_net/events` (Q7). Open for M3 design, not decided here: ASS `web`'s sign-in is Google via `web/auth`, not Keycloak — how a signed-in ASS Person becomes an LB2 on-behalf-of subject. LB2's `iss`+`sub` shape already admits a non-Keycloak issuer (`iss = accounts.google.com`, `sub = <google sub>`, `kind = human`, no schema change), and C8's role check applies to the acting subject; whether the host decides which Persons may run its agent (with its service account holding the role) or Google is brokered through Keycloak so the Person gets a Keycloak `sub` is authorization policy — LB2 lists it under Stays cheap, and architect confirms the choice at M3 design.
