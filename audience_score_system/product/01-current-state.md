# Current state

`audience_score_system` is genuinely new — no directory, no code, nothing reverted or half-built in this domain. Current state is entirely about what ASS should reuse from elsewhere rather than reinvent. Surveyed: `friendly_computing_machine/TOC.md` + `docs/microservices-architecture.md` + `temporal/` source, `tools/TOC.md` + `serial-mcp/README.md` + `agentsync-mcp/README.md`, `libs/TOC.md` + `libs/go/temporal`, `libs/go/db`, `libs/go/htmxauth`, `libs/python/alembic` READMEs, plus repo-wide grep for `youtube`/`oauth2`/`google-auth` and `valid_from` (SCD2 usage) and `git log --oneline -30`.

**Temporal — reusable, but two divergent integration patterns exist, pick one deliberately.**
- `friendly_computing_machine` runs the Python `temporalio` SDK directly (no shared lib): `temporal/worker.py`, `temporal/util.py`, and a hand-rolled `AbstractScheduleWorkflow` base (`temporal/base.py`) that wraps `ScheduleSpec`/`ScheduleIntervalSpec` for cron-like recurring workflows — this is exactly the shape "channel sync" needs, and it's the only in-repo *scheduled*-workflow precedent. It's real and working but bespoke to FCM (not a shared library) and its own comments flag it as uncertain in places ("not really sure what this is or how to use it properly").
- `libs/go/temporal` is the newer, hardened, *shared* Go bootstrap (`ConfigFromEnv`, `NewClient`, `NewWorker`, OTel tracing interceptor already wired) — built as the AR-4a foundation for `app_registry`, general-purpose, not FCM-specific. It has no scheduled-workflow helper equivalent to `AbstractScheduleWorkflow` yet.
- Net: "reuse Temporal" is unambiguous at the infrastructure level (same cluster, same `TEMPORAL_HOST` convention). It is not yet unambiguous at the code level — Go gets the hardened shared client/worker lib but no schedule helper; Python gets a working schedule pattern but no shared, non-FCM-owned library. ASS's language choice for its data-job worker determines which gap it inherits. Worth an explicit call in the design doc rather than assuming either "just reuse FCM's workflow" or "just reuse `libs/go/temporal`" transfers cleanly.

**OAuth — no self-serve Google/YouTube signup precedent exists anywhere in the repo.** `libs/go/htmxauth` is the closest structural analog (`Config`/`NewAuthenticator`, `HandleLogin`/`HandleCallback`/`HandleLogout`, `DBSessionManager` with AES-256-GCM-encrypted refresh tokens + auto-refresh-on-near-expiry + `SELECT FOR UPDATE` single-flight refresh) but it is generic OIDC against Keycloak, built for *login to an internal tool*, not *signup + per-provider (Google) consent-scope acquisition + role assignment*. Nothing in-repo does the "connect a third-party account and store scoped, refreshable, per-external-resource tokens" pattern ASS needs for both creator sign-in *and* per-Channel YouTube connection (these are two different OAuth-shaped things co-occurring at signup — the brief should be explicit that they're not the same grant). FCM's `gemini/ai.py` uses `google.generativeai` with an API key, not OAuth — not a usable precedent despite being "Google". `htmxauth`'s DB-session/refresh-token-encryption machinery is worth reusing for the *mechanics* of storing and refreshing the YouTube OAuth token even though the flow itself (consent screen, scope negotiation, account creation vs. login branching) is new.

**MCP server framework — clear, consistent precedent: Python + FastMCP.** Both existing MCP servers in `tools/` (`serial-mcp`, `agentsync-mcp`) and `tilt-mcp` are FastMCP-based Python, `bazel build`/`bazel run` targets, already vendored in `uv.lock` (no new dependency to negotiate). This is the idiomatic MCP implementation path here — ASS's MCP server should follow this shape (FastMCP + Bazel `py_binary`), not introduce a second MCP framework or a non-Python server exposing MCP.

**Postgres/SCD2/YouTube-client reuse:**
- `libs/go/db` is a thin, OTel-traced `pgxpool` wrapper (`PG_DATABASE_URL`) — the idiomatic Postgres access pattern for Go services. There is no equivalent shared Python DB-access library; Python domains (FCM) use SQLAlchemy via `libs/python/alembic` for migrations, not a shared query layer.
- SCD2 in the wild: `leaflab/migrate/migrations/011_scd2_naming.up.sql`+`012_views.up.sql`+`013_ownership.up.sql` and `tools/app_registry/migrate/schema/migrations/010_manifest_history.up.sql` are the worked examples AGENTS.md's convention describes — both are raw-SQL migrations run via `libs/go/migrate` (Go domains), not through `libs/python/alembic`. If ASS's MCP server is Python (per the FastMCP precedent above) but its schema is SCD2-shaped (Channel/Persona associations, schedule state per the intake), the migration tooling for that schema doesn't have a same-language precedent yet — either the raw-SQL `libs/go/migrate` pattern gets adopted cross-language (it's just a migration runner, not Go-specific in its output) or `libs/python/alembic` needs to grow SCD2-authoring conventions it doesn't currently have. Not a blocker, but a design-doc decision, not an assumption.
- No YouTube Data/Analytics API client exists anywhere in the repo (the one `youtube` grep hit was an unrelated code-comment link). This is a net-new external dependency — no reuse available, just noting so it isn't assumed to already be vendored.
