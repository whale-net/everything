# implement

Drives swimlane task execution against an existing Project board. The outer loop is an orchestrator, not a worker itself: it uses [`gh stack`](../../../../.claude/skills/gh-stack/SKILL.md) to give each task issue its own branch and PR, dispatches `worker`/`validator` subagents concurrently against those branches, then dispatches `mergepush` to register each batch's finished work into the plan's stack, open/refresh its PRs, and merge into `main` whatever is now `Done` and safe to land (CONVENTIONS.md § Continuous merge to trunk) — this pipeline is trunk-oriented, so most tasks land on `main` individually as soon as they validate rather than waiting for the whole plan. See `tools/project-manager/CONVENTIONS.md` § Git hygiene for the exact stacking mechanics referenced below, and § Worker lifecycle for swimlane query/advance mechanics.

**Responsibilities.** This orchestrator owns all shared git/`gh stack` state, but doesn't run every step of it inline: it creates every branch and its dedicated worktree itself, resolves any merge conflict that comes up while doing so (directly for a small conflict, or via an ad-hoc `general-purpose` merge subagent scoped to just that conflict when it's large or semantically ambiguous — CONVENTIONS.md § Git hygiene, "Division of responsibility"), then delegates registering each task into the plan's stack, creating/refreshing its PR (`gh stack link` — CONVENTIONS.md § Git hygiene step 5), and merging whatever is now `Done` and ready (CONVENTIONS.md § Git hygiene step 6) to a `mergepush` subagent, dispatched once per batch and waited on synchronously before the next swimlane scan — so `gh stack` operations stay exactly as single-threaded as before, just running in a subagent's context instead of this session's own. Because merging is delegated too, this orchestrator is also the one that resolves each batch member's current swimlane `Status` from the Project board before dispatching `mergepush`, so it can pass the `Done` subset in. Dispatched `worker`/`validator` subagents run entirely inside the worktree path they're handed: they edit files and commit on the task's branch, but never touch `git merge`, `gh stack`, or PR creation themselves — and neither, directly, does this orchestrator anymore. Branch creation (step 3c) never checks anything out in the shared checkout either — `git worktree add -b` creates a task's branch and its worktree together, so the shared checkout is never touched by anything in this whole flow.

**Plan stack.** Branch creation (step 3c below) still chains each task onto its own real `Depends on:` dependency, which can fork into a tree when two tasks share a dependency — but the plan needs to be reviewable as *one* `gh stack` stack, not a tree `gh stack` can't even represent (gh-stack skill § Known limitations #1). `mergepush` is what builds that one stack, via `gh stack link` (CONVENTIONS.md § Git hygiene step 5, "Why `gh stack link`, not a rebase" in `mergepush`'s own instructions) — not by rewriting any branch's history, just by registering each task's branch, in finish order, into the plan's stack. Unlike a stack held open and merged as a unit at the end, this one drains continuously: `mergepush` also merges the topmost currently-`Done`-and-ready prefix of the stack into `main` every batch (CONVENTIONS.md § Continuous merge to trunk), so the open stack at any point reflects genuine in-flight/blocked work, not the whole plan.

This orchestrator tracks `<plan-branches>`: every branch already registered into this plan's stack so far, bottom to top. Seed it at the start of a run — fresh or resumed, it doesn't matter which — by listing this plan's task issues that are past `Implementation` on the Project board (`Testing`, `Validation`, or `Done`; per § Worker lifecycle step 1's query shape) and ordering them by real dependency (each task issue's `Depends on:` line — for tasks with no dependency relationship to each other, any consistent order is fine, e.g. issue number). This is always recomputable from the Project board — a durable source of truth — so there's no in-memory-only state to lose across a resumed session, and no ambiguity to resolve: unlike a single "current tip" pointer, `<plan-branches>` doesn't need to identify one right answer among several candidates, because `gh stack link` accepts (and needs) the whole list every time anyway. Pass it into every `mergepush` dispatch (step 3e); after each dispatch returns, append that batch's newly-registered branches to it, in the order `mergepush` reports them.

## Usage

```
/project-manager:implement 123
/project-manager:implement 123 --max-subagents 2
```

- `--max-subagents <N>` — how many worker/validator subagents to run concurrently per batch. **Defaults to 4** if the user doesn't specify a number.

## Steps

1. `gh issue view <n> --comments` — confirm the root issue is labeled `plan:approved` and a `Project board: <url>` comment exists (extract the project number). If the label is missing, point the user to `/project-manager:design` or `/project-manager:review`. If the label is present but there's no `Project board:` comment yet, point the user to `/project-manager:plan <n>` first and stop.

2. **Stack prerequisites** (CONVENTIONS.md § Git hygiene step 1):
   ```sh
   gh extension list | grep -q github/gh-stack || gh extension install github/gh-stack
   git config rerere.enabled true
   git config remote.pushDefault origin
   git fetch origin main
   ```
   Also seed `<plan-branches>` per "Plan stack" above.

3. **Swimlane work loop.** Repeat until a full pass finds no ready unassigned work:
   a. Check active swimlanes in progression order — `Scaffold`, `Implementation`, `Testing`, `Validation` — for unassigned items scoped to this plan (query per CONVENTIONS.md § Worker lifecycle step 1), and confirm every issue in each candidate's `Depends on:` line is `CLOSED`.
   b. **Batch.** Take up to `max-subagents` ready candidates across swimlanes — phases can mix freely in one batch (e.g. a `Scaffold` candidate and a `Validation` candidate together).
   c. **Prepare each candidate's branch and worktree** (CONVENTIONS.md § Git hygiene step 3):
      - Branch name: `pm[<attempt>]-<n>/<task>-<slug>` (CONVENTIONS.md § Git hygiene step 2). Look for an existing `pm*-<n>/<task>-*` branch first (local, then remote) and reuse it if found; only compute a fresh `<slug>` from the task issue's title, with `<attempt>` omitted, when none exists.
      - If the branch doesn't exist yet (first phase dispatched for this task), create it and its worktree together with `git worktree add .pm-worktrees/<task> -b pm[<attempt>]-<n>/<task>-<slug> <parent>` — `main`, or chained onto its `Depends on:` branch(es). Record `<parent>` alongside the branch/worktree for this task — `mergepush` needs it later to isolate this task's own commits. A task with more than one dependency branch merges the rest in inside the new worktree (`git -C .pm-worktrees/<task> merge --no-edit <other-dep-branch>`) — if that merge conflicts, resolve it yourself before moving on, or, for a large/ambiguous conflict, dispatch an ad-hoc `general-purpose` subagent scoped to just that merge (CONVENTIONS.md § Git hygiene, "Division of responsibility"). Never hand an unresolved conflict to the worker.
      - This never checks anything out in the shared checkout, so unlike the old `gh stack init`-based approach, different candidates' branch creation can happen concurrently instead of one at a time — nothing here touches `gh stack`'s own state file either, so there's no lock to serialize against at this step.
   d. **Dispatch the batch in parallel** — one `Agent` call per candidate, all in a single message so they actually run concurrently:
      - `Scaffold` / `Implementation` / `Testing` candidates → `project-manager:worker` with `<n>`, `<project-number>`, `<Swimlane>`, the candidate issue number, and its worktree path.
      - `Validation` candidates → `project-manager:validator` with `<n>`, `<project-number>`, the candidate issue number, and its worktree path.
   e. **Wait for the whole batch to return, then dispatch `mergepush` once to integrate it and merge whatever's ready** (CONVENTIONS.md § Git hygiene steps 5-6): pass it `<n>` (the root issue), the current `<plan-branches>`, for every batch member — regardless of whether its phase advanced the swimlane or routed back — the same `<task-issue-number>`, `<branch-name>`, `<worktree-path>`, `<parent>` quadruple resolved for it in step 3c, in a fixed order, and `<done-task-numbers>`: re-query the Project board for every task in `<plan-branches>` plus this batch that's now `Status: Done`. For each task in order, `mergepush` cherry-picks that task's own commits (isolated via `<parent>`) onto a scratch branch built on the running stack tip, force-pushes the result to `<branch-name>`, then runs `gh stack link` with the running branch list plus that branch appended — this opens or refreshes its draft PR and corrects the PR's base so the plan stays one coherent stack, without ever needing `<branch-name>` checked out anywhere but its own original worktree — sets title/body on first creation (CONVENTIONS.md § Git hygiene, "PR content"), removes each original worktree as best-effort cleanup. It then merges the topmost `Done`-and-ready prefix of the stack into `main` via `gh stack merge` (nothing merges if none qualify yet — not a failure), and reports back one line per task — its PR URL and whether this created or updated it, or the exact error if a step failed — one line on what merged into `main` this batch (if anything), plus a final line giving the full updated `<plan-branches>`. This is the only point anything creates a PR or merges to `main` — worker/validator never do, and this orchestrator never runs `gh stack`/PR commands itself either, so their output never lands in this session's own context. Update your `<plan-branches>` variable from that final line. Collect the PR URLs, merge results, and any failures from `mergepush`'s report for step 4's summary; for a failed task, resolve it the same way an unresolved merge conflict from step 3c would be handled (inline, or an ad-hoc `general-purpose` subagent) before it's eligible for the next batch.
   f. Re-scan swimlanes after `mergepush` returns. Repeat from (a) until all tasks reach `Done` or a full pass finds no more ready unassigned tasks.

4. **Report.** Summarize progress across swimlanes, listing each task's PR URL and whether it has already merged into `main` or is still open (collected during step 3e, or via `gh pr view <branch> --json number,url,state` per branch). If every task is `Status: Done`, tell the user `/project-manager:validate <n>` is the next step — most tasks will typically already be on `main` by then via continuous merge, so that step mainly runs whole-system validation and lands whatever's left. If items remain blocked or waiting on dependency fixes, report them clearly.
